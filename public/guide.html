FastAPI serves both the frontend and API from one localhost origin. The frontend uses native JavaScript modules and local SVG icons; no Node server or frontend build is needed to run the app. Node is used by an optional interoperability test. AWS storage and managed authentication are future deployment work.

The API is trusted. Uploads are encrypted before they reach it. For downloads and inbox review, the API receives the encryption passphrase and temporarily handles decrypted content. This is not a server-blind or zero-knowledge architecture. Local HTTP is for development; deployment needs HTTPS.
02 / IDENTITY IS DIFFERENT FROM DECRYPTION

What belongs to a user?

Login identifies you

A local account has a user ID and an Argon2id-hashed login password with its own random salt. Login creates a random session secret in an HttpOnly, SameSite Strict cookie. SQLite stores its hash and expiry. The API uses this session to identify whose permissions to check.

There is no Clerk, Cognito, or PKCE login in the current local version.

The encryption passphrase unlocks your key

During normal account setup, the browser generates an RSA-OAEP key pair. It derives an AES key from the separate encryption passphrase using Argon2id and encrypts the private key before saving it. Only the public key and protected private key are persisted.

The demo seed script creates Alice and Bob’s keys server-side for convenience. User-created accounts generate keys in the browser.

Encryption passphrase + salt→ Argon2id →Key-encryption key (KEK)→ unlocks →User’s RSA private key→ unwraps →Version’s AES data key (DEK)→ decrypts →File + manifest
ItemBelongs toStored how?
Public/private RSA key pairOne userPublic key is readable; private key is AES-GCM encrypted under that user’s passphrase-derived KEK.
AES-256 data keyOne new uploaded versionA separate RSA-wrapped copy for each authorized user; no bare DEK is persisted.
Ownership and roleA user + a logical filefiles.owner_id and permissions rows.
Argon2id salt and noncesA key setup or encryption operationStored openly; they are not secrets. They let the correct operations be repeated.

Key protection uses Argon2id with 16 MiB memory, 2 passes, 1 lane, and a 32-byte output. Login hashing uses 3 passes. RSA-OAEP uses 2048-bit keys and SHA-256. File encryption uses AES-256-GCM with 12-byte nonces and 128-bit authentication tags. These are the current demo parameters.

  1. Identify the owner.Alice signs in. The API identifies her user ID from her session.
  2. Encrypt in the browser.The browser hashes the original bytes, generates a fresh AES key, encrypts the file and manifest, and wraps that AES key for Alice’s public key.
  3. Store the object.POST /api/files validates the encrypted upload and saves its ciphertext under a random object ID. SQLite gets a logical file, version, and Alice’s key envelope.

Bob or a guest: submit through Alice’s link
  1. Open Alice’s request./drop/#secret loads the upload screen. No login is required, and an existing login does not change the destination.
  2. Look up the link.The browser sends the secret in the JSON body to POST /api/drop/info. The API matches its stored hash and checks closure, expiry, and quota.
  3. Encrypt for Alice.The API returns Alice’s public key and request details. The browser encrypts the selected file and wraps its AES key for Alice, even if Bob is signed in.
  4. Store a pending submission.POST /api/drop/upload checks the link again, applies quotas, stores ciphertext, and creates a pending inbox row. No file is added to Bob’s vault, and no vault read permission is granted.
  5. Return a receipt.The uploader receives a submission ID. It is a receipt, not a credential for downloading the file.
Alice: review and accept a submission
  1. Read her inbox.Alice signs in. The owner-only inbox API lists pending metadata for her requests.
  2. Unlock and verify.Alice supplies her encryption passphrase. Python unlocks her private key, unwraps the submitted DEK, verifies GCM, decrypts the file and manifest, and checks original SHA-256 and size.
  3. Preview the verified bytes.The browser hashes the response again before displaying supported text, image, audio, or video content. Other formats can be downloaded for review.
  4. Accept or reject.Acceptance repeats integrity verification, then creates Alice’s logical file, first version, and key envelope using the existing encrypted object. Rejection keeps the submission outside the vault; ciphertext is retained in this local prototype.

What the token does

The request secret is generated from 32 random bytes. SQLite stores only its SHA-256 hash. The full link is shown once when created. The secret lives after # in the link, so the browser does not include it in the initial page URL sent to the server. JavaScript sends it in API request bodies.

Possession of this link authorizes uploads to that request. It does not authorize listing submissions, downloading files, or reviewing someone else’s inbox.

Limits stay in Python

Each file is limited to 25 MiB. A request defaults to 10 submissions, with a configurable maximum of 20, and a 100 MiB total limit. Creation supports 1–168 hours. The UI offers 1 hour, 24 hours, or 7 days.

The API checks expiry, closure, and quotas again on each submission. Limits include accepted and rejected files. Closing stops new uploads but keeps received files reviewable.

Sender identity is unverified. The public flow records an external submission, even when the uploader happens to be signed in. The optional name/email field is a label, not proof of identity. Integrity verification also does not mean malware scanning.
05 / ACCESS AND HISTORY

A shared recipient gets their own key envelope.

  1. Alice chooses registered Bob and a role.Only the owner can share. Bob must have completed key setup. The frontend obtains Bob’s public key from the API.
  2. Alice’s browser unlocks her private key.For sharing, her encryption passphrase is used locally in the browser. It unwraps each version’s DEK and wraps that DEK again using Bob’s public key.
  3. The API saves the grant and envelopes.POST /api/files/{id}/share stores viewer/editor permission and a wrapped key for Bob for every historical version. Alice’s passphrase is not part of this share request.
  4. Bob downloads using his own passphrase.The API checks Bob’s role, unlocks Bob’s private key, and uses Bob’s envelope to recover the DEK. Alice does not give him her passphrase.

New uploads create new snapshots

Every ordinary upload creates a fresh object, new data key, fresh nonces, encrypted manifest, version row, and envelopes for all current recipients. The file’s current-version pointer advances.

Restore reuses earlier ciphertext

Restore creates a new version row pointing to an earlier object and copies its envelopes and metadata. It does not re-encrypt that object or overwrite the old history. A corrupted earlier object cannot be repaired by restoring a pointer to that same object.

Revocation removes the grant and stored envelopes for that user. It blocks subsequent API access, but cannot erase plaintext or keys already downloaded. The UI’s delete operation hides the file while retaining encrypted history.

06 / THREE DIFFERENT CHECKS

Encryption integrity, byte checksums, and audit integrity.

CheckWhat happens?What it establishes
AES-GCM authenticationPython verifies the file and encrypted manifest tags. Their immutable object ID is bound as additional authenticated data, with separate :data and :meta contexts.A modified, truncated, or mismatched ciphertext fails verification; the API returns no plaintext.
SHA-256 comparisonThe browser hashes original file bytes before upload. Python compares decrypted bytes against the manifest hash, then the browser hashes the returned response again.The received bytes match the expected original bytes, subject to trust in the API returning that expected digest.
Audit hash chainEach event hashes its canonical serialized fields together with the previous event hash. Verification walks the chain and compares its final head with a separate checkpoint file.Changed audit events or a missing tail are detectable while the checkpoint remains trusted.

The persisted checksum is in the encrypted manifest. The current browser upload payload also includes a duplicate plaintext checksum field; the API does not persist that duplicate. File names, MIME labels, sizes, and access metadata are not all concealed.

The server trust boundary still applies. An API that controls the plaintext response can also replace a response checksum. The browser’s comparison catches accidental byte mismatches, not a malicious trusted API forging both values. Likewise, the local audit checkpoint is not a separate immutable cloud service; an attacker controlling both the database and checkpoint filesystem is outside this protection.
Why does the current UI ask for the passphrase on each download?
V1 unlocks keys for the operation and does not keep an unlocked private key between requests. A session-based “unlock vault once” experience was discussed but has not been implemented. Downloads, inbox preview, and acceptance decrypt in the API. Sharing decrypts key material in the owner’s browser. Passphrases are not saved in browser storage or the database.
What happens to audio and video?
They are encrypted as binary files using the same flow. The complete file is authenticated, decrypted, and checksum-verified before the browser gets a Blob URL for playback. This version does not provide large-file streaming or HTTP range-based seeking before the full file is loaded. Browser codec support determines preview support.

08 / A DEMO THAT TELLS THE WHOLE STORY

Two windows. One file. A complete path.

  1. Start locally and sign in as Alice.Run ./run.sh, then open http://localhost:3000. Use the prepared demo account details shown by the login page.
  2. Create an upload link.Choose Upload inbox → Create upload link. Copy the link while it is displayed.
  3. Submit in another window.Use incognito for the anonymous case, or sign in as Bob for the signed-in case. Both open the exact same link and encrypt for Alice’s public key.
  4. Observe the pending boundary.Alice sees the submission in her inbox, but it is not yet in All files. Bob has gained no read access.
  5. Verify, preview, and accept.Alice uses her passphrase. Show the checksum result, accept, and open the new file from her vault.
  6. Close the link and retry.The public page now reports that it is unavailable. Existing submissions remain reviewable.
  7. Show the independent security checks.Inspect ciphertext, verify the audit chain, and use a disposable object for a tamper demonstration. Do not corrupt a real user’s file.
Current scope: Local disk objects and SQLite; manual passphrase unlock per operation; no Recovery Center, no always-unlocked session, no passphrase recovery, no cloud deployment, and no malware scanning. Localhost links work on this machine; remote users need a deployed HTTPS address.
